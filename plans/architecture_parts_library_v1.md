## 核心问题

零件库涉及三个层面，需要协同设计：

1. **文件夹结构**：人工管理，git 版本控制
2. **pbg 配置文件**：LDCad 读取，决定软件内分类层级
3. **前端展示**：LDCad 零件面板的视觉层级（见截图设计）

---

## LDCad 加载约束（硬性限制）

LDCad `off` 类型库只认以下结构，不递归扫描子目录：

```
库根目录/
  parts/*.dat     ← 主件，只扫描这一层
  parts/s/*.dat   ← 子件，固定目录名
  p/*.dat         ← 图元（可选）
```

**结论：物理子目录分类对 LDCad 无效，分类只能靠 pbg。**

## 三种方案

### 方案 A：单库平铺（当前方向）

```
vex-iq-parts-v2/
  parts/
    *.dat          ← 所有主件平铺
    s/
      *.dat        ← 所有子件（含共享）平铺
```

- 分类完全由 pbg 控制
- **优**：LDCad 零配置，共享子件零摩擦
- **缺**：文件夹里零件多了不直观

---

### 方案 B：多库路径（每类目一个库）

每个分类注册为独立 `off` 库，各自有 `parts/` + `parts/s/`。

- **优**：文件夹结构 = 分类结构
- **缺**：共享子件必须在每个库复制，更新时容易出错；config 越来越复杂
- **结论：不推荐**

---

### 方案 C：源码分类 + 部署平铺（双层）

```
vex-iq-parts-lib（git 仓库，人管理）：
  L3/L4/
    pneumatics/*.dat
    beams/*.dat
    shared-s/*.dat     ← 共享子件统一管理

部署脚本 → 自动平铺到：
  vex-iq-parts-v2/parts/*.dat
  vex-iq-parts-v2/parts/s/*.dat
```

- **优**：源码直观，LDCad 结构不变
- **缺**：需要部署脚本，多一个环节

---

## 已定稿决策

**选方案 A**，与 LDraw 官方标准一致。

### 后续零件整理操作规范（每次新增零件必须遵守）

**文件放置：**
- 主件 → `vex-iq-parts-v2/parts/零件名.dat`
- 专属子件 → `vex-iq-parts-v2/parts/s/SKUs序号.dat`
- 共享子件（vexpin系列等）→ `vex-iq-parts-v2/parts/s/`，一处存放，不复制

**pbg 配套（前端展示）：**
- 新增零件类目 → 在 `sorted/` 下新建或更新对应 `.pbg`
- 新增套件类目 → 在 `sets/` 下新建 `.pbg`，并在 `sets.pbg` 的 `<items>` 中注册
- 每个 `.pbg` 的 `<items>` 中按顺序列出零件文件名

**图元（p/）规范（2026-04-18 调查确认）：**
- `p/` 只放标准 LDraw 图元（如 `4-4cyli.dat`）
- VEX 专属子组件（旧中文命名）不属于 `p/`，将来迁移到 `parts/s/` 并按 SKU 重命名
- 迁移时机：整理到对应主件时同步处理，不单独批量迁移

**2026-04-18 实测状态（测试通过）：**
- `p/` 共 437 个文件：标准图元 247 个 ✅，旧式中文子组件 190 个（待分批迁移）
- 内容哈希检测：0 个重复 ✅
- 气动件在测试环境渲染正常 ✅
